# خطة ربط Hikvision مع Dimah ERP

الجهاز: **DS-K1T342EFWX**. البرنامج الحالي: **iVMS-4200 / Service Manager Hik Control**.

المعلومات التي أكدها المستخدم: العنوان الداخلي `192.168.8.97`، إصدار `V4.38.0 build 20250109`، وكمبيوتر iVMS يعمل طوال الدوام. لا يلزم MAC Address لاختبار الاتصال الحالي.

## نتيجة فحص الاتصال والخطوة الحالية

نجح فحص TCP للمنفذين 80 و443 من الكمبيوتر الحالي. طلب GET دون بيانات دخول إلى `/ISAPI/System/deviceInfo` رجع HTTP 401 مع مصادقة Digest؛ هذا يثبت الوصول لواجهة محمية، ولا يثبت قراءة أحداث الحضور أو صحة بيانات الدخول أو سلامة شهادة HTTPS.

لإكمال القراءة افتح مجلد `tools` ودبل كليك على `check_hikvision_connection.cmd`. أدخل اسم المستخدم وكلمة مرور **جهاز البصمة** محليًا في نافذة الطلب. لا تُرسل كلمة المرور بالمحادثة. الفحص يقرأ معلومات الجهاز عبر Digest على عنوانه الداخلي، دون تغيير الإعدادات، ودون جلب موظفين أو قوالب بصمة أو أحداث. اتصال HTTP يستخدم مصادقة Digest ولا يستخدم Basic؛ تجهيز TLS بشهادة موثوقة يُراجع قبل تشغيل المزامنة الدائمة.

عند النجاح يُحفظ `build/hikvision_connection_report.json` بمعلومات الموديل والإصدار ونتيجة الفحص فقط، دون بيانات الدخول أو الرقم التسلسلي أو MAC. يمكن مشاركة هذا التقرير أو صورة النتيجة. أداة التشغيل تتجاوز سياسة سكربت PowerShell لهذه العملية فقط ولا تغيّر سياسة النظام.

أكد المستخدم نجاح تسجيل الدخول الفعلي يوم 2026-10-05، وظهر تقرير `device_information_read_successfully` للموديل `DS-K1T342EFWX` وإصدار `V4.38.0` وتاريخ `build 250109`. هذا يؤكد قراءة معلومات الجهاز؛ قراءة الأحداث والمزامنة لم تتأكدا بعد.

### الخطوة التالية: عينة أحداث

أكد المستخدم نجاح قراءة الأحداث يوم 2026-10-05. العينة الأولى كانت بلا هوية موظف، بأكواد عشرية 23 و27 و21 و24 و26؛ جدول Hikvision الرسمي يصنفها كأحداث زر الباب/حالة الباب/القفل. التوقيت يحمل إزاحة `+03:00`، ولا يثبت هذا وحده صحة ساعة الجهاز.

تم تحديث أداة `tools/check_hikvision_events.cmd` للبحث عن التحقق الناجح بالبصمة والوجه والبطاقة: النوع الرئيسي 5 والأكواد الفرعية العشرية 38 و75 و1، طبقًا لـ[جدول أحداث Hikvision الرسمي](https://open.hikvision.com/hardware/structures/NET_DVR_ACS_ALARM_INFO.html). شغّل نفس الملف وأدخل بيانات الجهاز محليًا. الفحص يقدم 3 طلبات بحث إلى `POST /ISAPI/AccessControl/AcsEvent?format=json`، صفحة واحدة لكل نوع وحد أقصى 5 أحداث لكل صفحة خلال آخر 7 أيام (15 حدثًا كحد أقصى). يرسل `picEnable=false` ولا يطلب صورًا أو قوالب بصمة. هذه عينة لبعض طرق التحقق، وليست قائمة شاملة للتحقق المركب. نجاح التحقق لا يثبت حضورًا أو انصرافًا؛ تشغيل البحث المعدّل ينتظر نتيجة المستخدم.

التقرير `build/hikvision_event_sample.json` يحتوي على نطاق البحث والعينات مقسمة حسب مرشح النوع وعدد الأحداث التي تحتوي على رقم موظف، ورقم الموظف داخل الجهاز وتوقيت الحدث ورقمه وتصنيفه وحالة الحضور وطريقة التحقق إن أرجعها الجهاز. تُستبعد الأسماء وأرقام البطاقات وروابط الصور وبيانات الدخول، ويُحد حجم كل استجابة إلى 1 MiB. تُستخدم العينة للتحقق من الربط فقط. لا يتم تفسير `minor` تلقائيًا كحضور أو انصراف، ولا يتم إنشاء أو تعديل سجلات Supabase.

لو ظهرت `sample_count: 0` يلزم مراجعة ساعة الجهاز ووجود بصمات حديثة. ولو رجع خطأ HTTP تُراجع استجابة هذا الإصدار قبل بناء المزامنة. يمكن إرسال صورة نتيجة الفحص؛ لا ترسل كلمة المرور. بعد نجاح العينة نحتاج مطابقة رقم الموظف داخل الجهاز مع الموظف في ERP والتأكد من حالات الحضور والانصراف وتوقيت الجهاز.

الملفات الجديدة: `check_hikvision_events.cmd` و`check_hikvision_events.ps1` و`hikvision_event_helpers.ps1` و`test_hikvision_event_helpers.ps1` داخل `tools`. اجتازت ملفات PowerShell الثلاثة فحص البناء، واجتازت اختبارات محلية لنطاق UTC وحد العينة واستبعاد الحقول الخاصة والحفاظ على أرقام الموظفين وحالات الأحداث والاستجابة الفارغة ورفض الاستجابة غير المتوقعة. هذه اختبارات محلية ببيانات مصطنعة، وليست إثباتًا لقراءة أحداث الجهاز. لم يتغير Flutter أو قاعدة البيانات في هذه الخطوة.

[مثال GET الرسمي لمعلومات الجهاز](https://www.hikvision.com/content/dam/hikvision/vn/webinar/Thang3_Hikvision_Tich_Hop_He_Thong_Overview-of-3rd-Party-Integration.pdf).

يدعم الموديل رسميًا ISAPI وISUP 5.0. ISAPI واجهة HTTP للأجهزة؛ وiVMS-4200 يدعم جلب الأحداث وتقارير الحضور وتصديرها. دعم البروتوكول لا يثبت أن جميع نقاطه متاحة في إصدار Firmware المثبت أو أن تعايش جمع الأحداث مع iVMS يعمل؛ يلزم اختبار الجهاز الفعلي.

المراجع: [مواصفات الموديل](https://assets.hikvision.com/prd/normal/all/doc/m000054137/DS-K1T342EFWX_Datasheet_20260506.pdf)، [مركز تكامل Hikvision وISAPI](https://tpp.hikvision.com/tpp/IntegrationCenter)، [دليل iVMS-4200 AC](https://www.hikvision.com/content/dam/hikvision/en/support/download/vms/ivms4200-series/software-download/v3-7-0-5/UD26609B_iVMS-4200-AC-Client_User-Manual_V1.7.0_PDF1-TEST_en-US_20211221.PDF).

## المسار المقترح

خدمة Windows على كمبيوتر دائم التشغيل في شبكة الجهاز تقرأ أحداث الحضور عبر ISAPI دوريًا، ثم ترسلها باتصال HTTPS إلى واجهة خادم مُصادق عليها في Supabase. يظل iVMS-4200 يعمل كما هو أثناء تجربة القراءة الأولى. لا حاجة لتعريض عنوان الجهاز على الإنترنت أو وضع بيانات دخوله في Flutter.

```mermaid
flowchart RL
  device[Hikvision في الشبكة الداخلية] --> bridge[خدمة مزامنة Windows]
  bridge --> api[واجهة استقبال آمنة]
  api --> events[أحداث حضور خام مع منع التكرار]
  events --> attendance[سجلات حضور الموظفين]
  attendance --> erp[Dimah ERP]
```

## قبل التنفيذ

المطلوب: IP الجهاز، إصدار Firmware، نسخة iVMS، كمبيوتر يعمل طوال الدوام، عينة تقرير حضور أو أحداث، معرفة رقم الشخص في الجهاز لكل موظف، سياسة الدوام والورديات والمنطقة الزمنية. تُدخل بيانات الجهاز محليًا عند التجربة ولا تُرسل في المحادثة.

أول اختبار سيكون قراءة معلومات الجهاز وإمكانياته وأحداث قليلة لفترة محددة فقط، دون تعديل المستخدمين أو إعدادات الجهاز. بعد تأكيد أسماء حقول الأحداث ودلالات دخول/خروج، تُنفذ خدمة المزامنة.

## متطلبات التنفيذ التالي

- ربط **رقم الشخص/الموظف في الجهاز** بمعرف الموظف في ERP؛ الأسماء وحدها غير كافية.
- جدول أحداث خام مع هوية الجهاز وهوية الحدث والتوقيت الأصلي والمنطقة الزمنية. مفتاح فريد يمنع إعادة استيراد الحدث.
- حفظ نقطة آخر مزامنة بعد نجاح الكتابة، وإعادة قراءة فترة متداخلة قصيرة لمعالجة الانقطاع، ومنع التكرار في الخادم.
- حفظ الأحداث غير المربوطة بالموظفين للمراجعة؛ لا تُنشأ حسابات أو موظفون تلقائيًا.
- فصل أحداث الدخول/الخروج الحقيقية عن فتح الباب والإنذارات، وفق حقول الموديل الفعلية.
- تحويل الأحداث إلى أيام عمل حسب الوردية، مع دعم الانصراف بعد منتصف الليل وعدم اعتبار كل حدث فتح باب حضورًا.
- منع الاستيراد من الكتابة فوق تصحيح معتمد؛ الاحتفاظ بالأصل والتصحيح والمصدر للتدقيق.
- عدم نقل صور الوجه أو قوالب البصمة إلى ERP؛ المطلوب لهذه الوظيفة هو أحداث الوقت وهوية الموظف فقط.
- واجهة استلام مُقيدة بالشركة والجهاز، ومفاتيح قابلة للإلغاء، دون service_role في تطبيق الموظف.

يمكن تجربة ملف التصدير من iVMS باستخدام الاستيراد الحالي في شاشة الموارد البشرية. أضيف الآن نموذج المزامنة كل دقيقة مع استقبال SQL وحفظ الأحداث ومنع التكرار: [دليل التجربة والتفعيل](hikvision_automatic_sync.md). أكدت صورة المستخدم نجاح أول دفعة حية. أضيف إعداد تشغيل مخفي تلقائيًا عند دخول حساب Windows، مع حفظ كلمات المرور مشفرة؛ يلزم تشغيل الإعداد على كمبيوتر الدوام والتحقق من حالته. هذه مهمة عند تسجيل الدخول وليست خدمة تعمل قبل تسجيل الدخول.
